# 운영페이지 데이터 수정 병합저장 DB 설계서

## 0. 문서 목적

`PUT /api/v1/page-data/{slug}/{id}` 수정 저장 시 `page_data.data_json`을 **통째 교체가 아닌 병합**으로
반영하는 기능의 DB 관점 설계서.

**결론: 이 기능은 DB 스키마 변경이 전혀 없다.** 본 문서는 "왜 변경이 없는지"와
`data_json` 키의 수명주기(어떤 키가 언제까지 남는지)를 기록하여, 이후 에이전트가 신규 컬럼/이력 테이블을
검토하지 않도록 근거를 남기는 것이 목적이다.

---

## 1. 스키마 변경 여부: **변경 없음**

| 항목 | 변경 여부 | 근거 |
|:---|:---|:---|
| 신규 테이블 | ❌ 없음 | 기존 `page_data` 테이블 그대로 사용 |
| 신규 컬럼 | ❌ 없음 | 병합은 애플리케이션(Java Map) 레벨에서 수행, 저장 대상은 기존 `data_json` 하나 |
| 신규 인덱스 | ❌ 없음 | 접근 경로가 `id + data_slug` 단건 조회로 동일 |
| 제약조건 | ❌ 없음 | 변경 없음 |
| 마이그레이션 | ❌ 불필요 | 기존 행의 값을 건드리지 않음 |

> 대상 범위는 `page_data`(JSONB) 기반 Slug 타입 페이지에 한정한다.
> Data Entity 연동(`connectedType='entity'/'data'`) 경로는 커스텀 RDB 테이블에 컬럼 단위로 저장되므로
> 이 병합 정책의 적용 대상이 아니다.
> 테이블 상세 스키마는 [db_page-data.md](../page-data/db_page-data.md) 참조.

---

## 2. `data_json` 키 수명주기 / 병합 정책

`data_json`은 스키마가 고정된 컬럼 집합이 아니라, 템플릿(빌더 설정)이 그때그때 정의한 키:값 쌍의 집합이다.
템플릿은 시간이 지나며 필드가 추가·삭제되고, 조건부 표시(`hideCondition`)로 특정 필드가 화면에서 빠지기도 한다.
따라서 "이번 저장 요청에 담긴 키 집합"과 "행에 이미 저장돼 있는 키 집합"은 일치하지 않는 것이 정상이다.

**저장 시 키별 처리 규칙:**

| 케이스 | 요청 `dataJson`에 키 존재 | 처리 |
|:---|:---|:---|
| 화면에 표시된 필드 (값 입력) | O | 요청 값으로 **덮어쓰기** |
| 화면에 표시된 필드 (값 비움) | O (빈 문자열 `""`) | 빈 문자열로 **덮어쓰기** (삭제 아님) |
| `hideCondition`으로 숨겨진 필드 | X | 기존 DB 값 **보존** |
| 템플릿에서 제거된(구조적으로 빠진) 필드 | X | 기존 DB 값 **보존** |

- 중첩 객체(`contentKey` 하위 섹션, `_rel` 등)는 **재귀 병합**한다 — 섹션 전체가 요청에 없으면 섹션 통째로 보존, 섹션은 있고 내부 키만 빠졌으면 그 키만 보존.
- 배열(SubList `rows`, MultiSelect id 배열, 파일 ID 배열)은 **병합하지 않고 통째 교체**한다 — 요청에 배열 키가 있으면 요소 단위 병합 없이 그 배열이 최종값이 되고, 키가 없으면 기존 배열이 보존된다.

**키 정리(GC) 정책:**
템플릿에서 제거된 키는 이 정책상 행에 **영구적으로 남는다.** 사용하지 않는 키를 자동으로 지우는 정리 기능은
두지 않는다 — "쓰지 않는 키가 남아 있는 것"보다 "다시 필요해질 값이 조용히 사라지는 것"의 비용이 크기 때문이다.
특정 키를 실제로 없애야 할 때는 운영 판단으로 아래와 같이 직접 처리한다.

```sql
-- 특정 slug의 특정 키를 일괄 제거 (운영 판단 시에만 수동 실행)
UPDATE page_data
   SET data_json = data_json - 'legacyField'
 WHERE data_slug = 'sample-slug'
   AND data_json ? 'legacyField';
```

## 3. PostgreSQL 병합 연산자를 쓰지 않는 이유

`data_json = data_json || CAST(:req AS jsonb)` 형태의 DB 레벨 병합은 사용하지 않는다.
JSONB `||`는 **최상위 키만 보는 얕은 병합**이라, `contentKey` 하위 섹션이 통째로 교체되어
같은 섹션 안의 숨겨진 필드 값이 그대로 사라진다.

```sql
-- 얕은 병합의 문제 — content 섹션 내부의 memo가 유실된다
SELECT '{"content":{"title":"A","memo":"M"}}'::jsonb || '{"content":{"title":"B"}}'::jsonb;
-- → {"content": {"title": "B"}}
```

중첩 깊이에 관계없이 키 단위로 보존하려면 재귀 병합이 필요하므로, 병합은 애플리케이션(Java `Map`) 레벨에서
수행한다. 구체적인 병합 절차와 검증 규칙 적용 시점은 [be_page-data-merge-update.md](../../pages/page-data-merge-update/be_page-data-merge-update.md) 참조.
