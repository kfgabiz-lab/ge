# 00-4. Bo 빌더 에이전트 공통 원칙

이 문서는 Bo 빌더 파이프라인의 모든 에이전트(bo-builder, bo-code-reviewer, bo-architect-reviewer,
bo-design-bridge, bo-refactoring-specialist, bo-qa-validator, bo-security-reviewer)가
공통으로 지켜야 할 원칙을 모아둔 곳이다.

> 원래 각 에이전트 파일에 개별적으로(또는 누락된 채로) 흩어져 있던 원칙들을 여기로 모았다.
> 사고 하나가 나서 새 원칙이 필요해지면, **개별 에이전트 파일에 바로 적지 말고 이 문서에 먼저 추가한 뒤**
> 각 에이전트는 "이 문서 참조"로만 연결한다. (판단 기준은 `bo-orchestrator.md`의 "전파 판단" 원칙 참고)

---

## 1. 재사용 탐색 원칙

각 에이전트 파일에 있는 재사용 후보 표(스타일 상수, 공통 컴포넌트, 공통 함수 목록 등)는
**대표 항목일 뿐 전체 목록이 아니다.** 표에 없다고 바로 새로 만들지 않는다.

- 대상 기능과 관련된 폴더(`builder/fields/`, `renderer/`, `_shared/utils.ts`, `styles.ts` 등)를
  Glob/Grep으로 **넓게** 탐색한 뒤에만 "기존에 없다"고 판단한다
- "확인했다"는 말만으로는 인정되지 않는다 — 실제 탐색 이력을 산출물로 남긴다

### 산출물 (개발 담당 에이전트가 작업 완료 시 반드시 생성)

```json
// C:\tmp\bo-agent-comms\reuse-check-result.json
{
  "agent": "<에이전트명>",
  "timestamp": "<ISO8601>",
  "reuse_check": {
    "performed": true,
    "searched_in": ["실제로 Glob/Grep/Read로 탐색한 파일·폴더 전부 나열 — 개수·범위 제한 없음"],
    "existing_found": ["재사용 가능해서 실제로 가져다 쓴 기존 함수/컴포넌트명"],
    "new_created": ["이번에 새로 만든 함수/컴포넌트명 (없으면 빈 배열)"],
    "justification": "new_created가 1개 이상이면 기존 것으로 불가능했던 구체적 이유 필수 (공란 금지)"
  }
}
```

이 파일이 없거나 `reuse_check.performed=false`이거나, `new_created`에 항목이 있는데
`justification`이 비어있으면 **critical 이슈**다.

## 3. styles.ts 공통 상수 — 직접 작성 금지

```typescript
// ❌ 금지
className="border rounded px-3 py-2 text-sm focus:ring-2 bg-white"

// ✅ 올바름
import { inputCls, selectCls, btnPrimary, btnSecondary } from '../../styles';
className={inputCls}
```

| 상수 | 용도 |
|------|------|
| `inputCls` | input 기본 스타일 |
| `selectCls` | select 기본 스타일 (appearance-none, pr-8 포함) |
| `btnPrimary` | 주요 버튼 (bg-slate-900, text-white) |
| `btnSecondary` | 보조 버튼 (border, text-slate-700) |

## 5. preview/live 모드 분리 원칙

```typescript
// ❌ 금지 — UI 요소를 숨기거나 레이아웃 변경
{mode !== 'preview' && <input ... />}

// ✅ 올바름 — UI는 동일, 기능만 비활성
const isPreview = mode === 'preview';
<input disabled={isPreview} onChange={isPreview ? undefined : handleChange} ... />
```

- preview 모드에서 UI 요소를 숨기거나 레이아웃을 바꾸지 않는다
- `disabled={isPreview}` 또는 `onClick`/`onChange` 무시 패턴만 사용한다
- preview/live 양쪽에서 동일한 UI가 렌더링돼야 한다

## 7. entity 연동 판단 원칙

> 실사고 사례: connType='api' 대상이 entity에 연결돼 있는데 "이 connType은 entity와 무관하다"고
> 임의 판단해 camelCase 변환을 빠뜨려 `MALFORMED_JSON` 400 발생
> (`docs/ge_guide/builder/06.builder_entity_to_api_guide.md` §8 참고).
> QA 단계에서는 이 구조적 실패를 "우리 화면 문제 아님"으로 non-blocking 처리해 실사용자단 버그를
> 놓친 사례도 있었다.

- 저장/조회 대상이 Slug Entity(Data Entity) 연결인지 확인한다 — `api_info.connectedEntity` 또는
  `pageIsEntity`/`isEntity` 여부로 판단. **connType이 무엇이든(content/datasave/api 등) entity에
  연결돼 있으면 예외 없이 적용한다**
- "이 connType은 entity 연동 대상이 아니다"라고 근거 없이 단정하지 않는다
- entity 연결 저장은 아래 두 단계를 모두 거쳐야 한다:
  1. `buildDataJson(..., isEntity: true)` — 중첩 없이 flat 구조로 조립
  2. `buildEntityRequestBody`(`entityApi.ts`) — `toEntityFieldName`으로 camelCase 변환
  → 1단계만 하고 2단계를 빠뜨리면 필드명이 어긋나 `Unrecognized field`/`MALFORMED_JSON` 400이 난다
- 검증(QA) 단계에서 entity 연결 API가 구조적 원인(필드명 불일치, nested/flat 불일치, camelCase
  미변환 등)으로 실패하면 **Critical** — "우리 위젯 자체는 정상 동작했다"는 이유로 non-blocking
  Info 처리하지 않는다. 업무적 원인(필수값 미입력 등 정상 validation)만 Info/Warning으로 하향 가능
